# 状态、故障溯源与恢复会议

日期：2026-10-21。审查基线：0.4.4，2494a46a42c9d5492cbaa9034d36e70d7fe7937e。

目标：软件允许发生故障，但必须保留发生经过、已确认事实、数据保存情况及下一步。本文是会议形成的开发提案；新增探测、冷却、动作回执与时间线尚未实现，不能作为已验收能力。

参会分工：主控负责组合与用户流程，state_contract_meeting 审查领域状态，recovery_trace_meeting 审查溯源及恢复，practical_qa_meeting 审查操作和验收。子智能体进行只读审查并交叉质疑；本轮没有执行真实平台请求、修改运行数据或发布版本。

## 1. 共识与当前缺口

| 事项 | 0.4.4 当前情况 | 下一轮工作 |
| --- | --- | --- |
| 任务、认证、保存状态 | 已分别保存；部分页面仍用“需要登录”概括多种原因 | 统一说明原因和可执行动作，不用一个总状态代替各层事实 |
| 范围结束记录 | 抖音搜索、评论、回复已有按轮次记录 | 补详情及预期范围登记；其他平台分别标注覆盖程度 |
| 原任务恢复 | 已有原任务/数据集重放去重及同账号认证续接规则 | 明确重放可能重复经过页面，不能宣称精确游标续跑 |
| 等待时主动停止 | 后端可关闭认证续接，但状态仍是 needs_login，页面缺入口 | 提供“停止自动续接”，状态与行为都可核对 |
| 检查登录、打开平台、重试保存 | 已提交后台任务；界面没有持续绑定返回任务编号 | 保留本次动作编号与轮次，区分受理、执行中、完成、失败 |
| 故障历史 | 有事件、worker日志、轮次JSONL及最近checkpoint | 补关联与分页时间线；摘要截断不能丢失明细入口 |
| 采集可用性检查、冷却 | 尚无统一正式模型或验收 | 在停止、动作关联、范围记录补齐后实现 |
| 轮次与停止防护 | 登录/浏览器已有围栏；采集落库及最终状态更新仍有缺口 | 通过停止竞态、旧轮次迟到写入用例复现后修复；不据此断言历史数据已污染 |

具体依据：queue.py 的 control、最终任务更新和 collect_record；auth.py 的 platform_view；session_store.py 的 view/resume_matching；tools/crawl_status.py；Workbench.tsx 的 startLogin 与任务按钮；PlatformLogin.tsx 的更多操作。

## 2. 四类状态分别说明

| 类别 | 回答的问题 | 拟使用的表达 |
| --- | --- | --- |
| 平台会话 | 是否保存账号？这次是否确认登录？ | 保存成功/保存失败；认证有效/未登录/待人工验证/本次未确认，另列最近成功时间 |
| 采集可用性 | 哪个采集动作现在可用？ | 未检查/可用/网络异常/疑似限制/明确限制/接口异常/不支持，绑定平台、动作、检查时间 |
| 任务执行 | 现在执行到哪里，为什么等待？ | 排队/执行中/等待登录或验证/等待网络/等待冷却/正在停止/已结束 |
| 范围结果 | 已保存多少，哪些范围结束了？ | 按设置数量结束/平台本轮结束/本轮无结果/部分完成/未完成/未执行/用户停止 |

“等待”要展示具体原因；“结束”要展示结果。登录仍有效时，评论接口仍可能不可用。临时检查失败不能抹掉上次成功认证，也不能把上次成功当作本次在线确认。

保持现有 API v1 字段兼容，新增解释与动作投影；避免同时维护互相矛盾的多份状态。自检流程结束、检查通过、导出完成及分析覆盖完成也应分别解释，不让一个 completed 代替所有判断。

## 3. 证据与下一步合同

| 观察到的情况 | 可以下的结论 | 软件动作 | 用户或 Agent 下一步 |
| --- | --- | --- | --- |
| 正常响应并明确无下一页 | 本轮可返回范围结束 | 保存结束依据和已有数据 | 查看数据；不要宣称全站采全 |
| 正常成功码、空列表及结束标志 | 平台本轮返回无结果 | 正常结束该范围 | 如需排查，可主动检查可用性；不对每个正常空结果自动加请求 |
| 重复页、游标不前进、缺分页字段 | 尚未确认范围完整 | 保存已收数据并停止该范围 | 查看具体范围及响应摘要；修复原因后恢复 |
| 本机 API 授权失败 | Agent 与软件连接存在问题 | 保留平台账号与业务数据 | 使用当前 MD 的客户端和实例信息重新连接；不因此要求平台扫码 |
| 网络失败或超时 | 本次网络检查或请求未成功 | 在统一预算内重试，耗尽后暂停 | 检查网络并重试原任务；超时不能等同风控 |
| 平台明确未登录 | 认证需要恢复 | 暂停依赖该账号的任务，释放队列 | 登录；同账号确认及保存成功后仅续接符合条件的原任务 |
| 验证码、手机确认 | 需要人工操作 | 显示对应浏览器与具体提示 | 用户完成平台验证，再检查；不反复自动扫码 |
| 有效登录但保存失败 | 当前认证与持久保存结果不同 | 保留最近有效快照，报告保存失败 | 重试保存；仍失败时检查本机存储，不能反复登录代替修复 |
| 明确的限流或限制提示 | 本次操作受平台限制，影响范围依证据确定 | 保存依据，暂停受影响采集并冷却 | 遵循平台提示；到期重新检查，不承诺自动解封 |
| 原任务与对照探测均异常 | 疑似限制、接口或环境异常 | 保留“不确定”及其他排查结果 | 打开同一平台环境人工查看，或等待一次低频复查；不能直接确诊账号风控 |
| 单内容删除、私密或无权限 | 该内容当前不可读 | 仅登记该范围，不推导整账号被限制 | 跳过此内容或提供可访问来源；别让一个内容阻塞整个平台 |
| 已知响应结构不兼容 | 软件适配需要检查 | 停止反复网络重试，保留安全摘要 | 导出诊断信息，修复适配后恢复 |
| 本机读写或清理失败 | 数据提交或进程释放未确认 | 不误报保存成功；必要时阻止争用同一资源的后续任务 | 处理磁盘/权限/占用，再重试保存或清理 |
| 用户停止 | 不再自动执行该任务 | 禁用所有待执行续接，保存已有数据 | 用户明确点击恢复后才重新运行 |

证据至少包括来源层、时间、任务/轮次、平台与采集动作、范围、HTTP/业务状态、分页标志、游标、列表数量、耗时及相关事件编号。只保留结构白名单，不记录 Cookie、token、认证头或完整原始响应正文。

事实、解释、动作分开：例如“返回空列表”是事实，“疑似限制”是解释，“暂停并在指定时间复查”是决定，“复查是否成功”是动作结果。HTTP 403 必须说明来自本机软件还是平台；平台 403 也不单独等于账号封禁。

## 4. 探测与冷却

- 搜索异常才使用搜索对照词；评论、回复、详情各自检查。对照内容使用最近确实成功读取的公开来源，但仍允许该来源后来删除或失效。对照失败不是确诊证据。
- 每次只做少量、有限时限的读取；探测数据不进入正式任务、数据集或分析成果。失败记录和判断摘要保留。
- 同平台、同环境、同采集动作的并发请求复用一次探测；最近成功只作为带时间的证据，不能永久视作可用。
- 尚未检查的能力不等同失败，也不能永远挡住首次使用。允许在统一预算内执行用户原目标的首个请求，成功后正常继续；不把探测或全套自检变成所有任务的强制前置步骤。
- 限制范围不明确时，先保守暂停该平台采集；明确仅某动作或内容受影响时，缩小暂停范围。其他平台继续其各自检查，不保证它们必然正常。
- 根据用户经验，建议首次冷却默认至少60分钟并可调整；这是产品策略，不是平台恢复承诺。若平台要求更久，以平台要求为准。
- 到期仅重新检查受影响动作，成功才解除对应等待；失败延长等待，并设置有限自动复查次数，随后交由用户处理。具体预算在实现合同中固定，不能无限复查。
- 冷却与复查计划持久保存，重开软件不清零。重新认证只能解除认证阻塞，不能直接解除另存的访问限制。
- 统一计算实际请求和时间预算，防止底层客户端重试、队列重试和探测相乘。用户停止优先于任何定时或认证续接。

## 5. 能溯源的最小记录与动作

保留原始事实记录，并由统一判断模块生成当前解释、原因码、证据链接、规则版本、允许动作及恢复条件。界面与 Skill 读取同一份解释；无需 Agent 临时拼装检测脚本或猜测账号状态。

每次动作保留编号、来源请求、任务/轮次、作用范围、受理时间、执行状态与执行结果。受理成功不等于执行完成。失败时提供新的原因及下一步；旧页面、旧轮次及旧账号的动作不得覆盖新的状态。

预期范围在执行前登记，动态发现新内容时再增加范围。分别统计计划、已尝试、已确认结束、异常及未执行范围；还要区分接收条数、有效唯一条数、重复条数与实际成功持久化条数。分母只使用已知范围，不伪造全站覆盖率。

事件、范围记录及写入结果关联到同一任务和轮次；最终状态更新检查当前任务状态和轮次。每轮历史保留，任务详情提供分页。当前只展示前20个问题可以保留，但须提供全部记录与总数入口。清理列表与停止执行是不同操作：仍可能自动恢复的任务不能被静默隐藏，应提示先停止自动续接或保留可见等待入口。

现有 checkpoint.saved_records 是整个数据集累计去重后的记录数，并非本轮新增数；insert_records 已返回插入、更新、未变化数，但 collect_record 尚未将这些结果记入轮次。下一轮需明确累计数、本轮新增/更新/重复数，避免恢复后把旧数据当作新增成果。

原始JSONL和业务SQLite目前是先后写入，并非同一事务；若两者写入结果不同，需保留各自提交状态及恢复线索，不声称跨文件原子提交。先保证业务记录、轮次计数、相应事实在同一数据库事务中确认，外部文件按可核对方式恢复；客户端动作复用现有持久回执。

不重做为通用工作流引擎，不要求全面事件溯源重建业务数据库。优先扩展现有队列、任务事件、范围结束记录和客户端回执。少量版本化历史可以兼容旧日志，但需要独立索引、去重约束和并发比较的调度状态不应隐式藏在日志文本中；如需专用表，在实施规格明确迁移、先备份并验证兼容。本次会议不会修改当前schema4。

每个动作还应绑定判定修订号、账号绑定及运行轮次。并发或迟到动作再次执行前检查这些条件；旧判断允许展示为历史，却不得直接驱动新环境。稳定账号绑定与generation的职责不同，generation变化不能成为清空限制记录的理由。

## 6. 操作验收与开发顺序

沿用已确认的 HTTP/已安装 Skill、业务恢复、诊断生命周期、Electron/安装四类验收接口。每个动作都验证“点击→请求被受理→执行中→完成或失败→刷新/重开仍可追踪”，不能用按钮存在或请求200替代实操成功。

1. 先补等待任务停止入口、动作与轮次关联，以及旧轮次落库/停止竞态的失败回归，再完成最小修复。
2. 补详情与预期范围、完整历史查询、错误来源与可执行下一步；统一界面和客户端解释。
3. 再实现单次探测、共享探测、持久冷却、预算和有条件续接，用故障注入和可控时钟验证，不修改正式任务接口来接受测试 worker。
4. 在真实软件窗口逐个执行登录、检查、打开平台、重试保存、停止等待、账号确认、恢复与失败处理；先以抖音少量数据验证，再逐个平台登记结果。

最低矩阵：正常终页、正常空结果、重复页、缺字段、断网、本机授权失败、明确登出、验证码、保存失败、单内容删除/私密、接口变化、明确限流、疑似限制、探测未执行或失败、冷却重启与到期、用户停止、停止竞态、换账号、旧轮次迟到、重复点击、双客户端、页面刷新、响应丢失与同编号重试、历史查询及诊断脱敏。

确定性模拟可以证明状态与动作规则，不能证明真实平台解除限制。真实冷却恢复必须按实际等待和响应记录，不能用推进测试时钟冒充。七平台真实检查未完成时逐项标待验证，不把一条成功路径或自检通过扩展为全功能通过。

## 7. 已有实测边界

0.4.4 已有一次抖音有界实测：需要登录后，同一搜索任务在用户登录后第2轮自动续接，保存1条内容；随后详情与1条评论读取成功。正常预算包内自检通过。本机全量716通过、2跳过、1失败（旧版可复现的1.8秒自检清理测试）；独立CI为710通过、9跳过。

本次会议未增加上述实测范围。现有登录界面模拟、源码字符串检查和内部规则测试不能冒充完整真人操作链路；冷却、探测及新增状态仍需开发和验收。
