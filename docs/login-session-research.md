# 登录状态保存与简化体验：研究建议

研究日期：2026-09-22。基于当时源码、本机安装状态、独立本机实验以及浏览器官方文档。本文保留实施前的研究记录；后续实现及验证见 [0.1.1 登录会话升级](LOGIN_SESSIONS.md)。

## 推荐结论

默认提供“首次登录、自动记住、按需验证、失效后续接”的体验。用户不需要理解 Cookie，不需要复制字符串，不需要另外安装插件或配置服务器。

采用专用浏览器档案作为主存储，使用 Windows 加密的认证状态快照补充恢复能力；把不必要的登录提示、错误分类和浏览器反复启动一起解决。继续用独立 Chrome／Edge／Chromium 完成平台认证，桌面 WebView2 负责工作台界面。先固定当前已验证的浏览器，减少迁移变量。

## 当前软件已经做到什么

以下是本机证据，不是对七个平台普遍成功率的承诺。

- `config/base_config.py` 已启用 `SAVE_LOGIN_STATE`。
- 浏览器数据位于 `%LOCALAPPDATA%/MediaWorkbench/data/browser_data`，与程序安装目录分开。
- 本机抖音实际使用 Chrome 和 `cdp_dy_user_data_dir` 专用档案；不是平时浏览器的默认档案。
- 抖音在 2026-09-22 16:34 确认登录后，16:35、16:53 的任务启动均记录 `authenticated` 和 `restored=1`，说明保存状态已经在两次运行中成功复用。
- 小红书有浏览器目录，但没有成功认证记录。其他五个平台尚未完成真实账号验证。
- 当前已支持对用户传入的 Cookie 使用 Windows DPAPI 加密；没有统一自动保存浏览器认证快照。

检查中只读取认证状态、时间和浏览器目录信息，没有导出真实 Cookie。正在运行的抖音 Cookie 数据库被浏览器锁定，本次没有关闭采集、解锁或复制它。

相关实现：[`workbench/auth.py`](../workbench/auth.py)、[`workbench/credentials.py`](../workbench/credentials.py)、[`tools/cdp_browser.py`](../tools/cdp_browser.py)、[`tools/browser_launcher.py`](../tools/browser_launcher.py)。

## 为什么有保存，还会觉得麻烦

| 发现 | 证据及确定程度 | 应对 |
|---|---|---|
| 暂时无法验证也进入登录流程 | `managed_login` 首次探测异常被转成 `unknown`，只有 `authenticated` 会直接返回；其他结果进入 `opening_login`。已确认代码行为。 | 网络异常先重试并保留档案，无法确认时提示待验证；明确未登录才启动重登。 |
| 备用启动路径换了一份档案 | CDP 使用 `cdp_<平台>_user_data_dir`，标准模式使用 `<平台>_user_data_dir`。已确认路径不一致，但未证明它导致了此前抖音失效。 | 为账号绑定浏览器及档案；启动失败先恢复原路径，不能悄悄换成空档案后要求扫码。 |
| 每个任务拥有并关闭浏览器 | 平台任务各自启动，`main.async_cleanup` 关闭，Windows 最终清理还可能强制结束进程。已确认生命周期；没有证据认定所有强制清理都会丢 Cookie。 | 正常退出时先保存、再关闭、等待进程结束；后续让同批任务复用由后台管理的浏览器。 |
| 浏览器种类未绑定账号 | 未设置自定义路径时，每次重新检测 Chrome／Edge；没有账号与浏览器引擎的绑定记录。 | 保留当前可用浏览器，新装浏览器不自动替换已有账号的环境。 |
| 登录凭据更新没有统一管理 | 抖音客户端在部分节点从浏览器更新 Cookie，请求层没有统一把响应中新凭据同步回浏览器并保存的机制。已确认实现缺口，但未证明当前任务受此影响。 | 按平台验证 Cookie 更新方式，避免任务一直持有启动时的旧值；仅保存验证过的最新状态。 |
| 界面容易把验证当作登录 | 已登录卡片仍有“验证登录”，成功验证不明确表示本机保存已经完成。 | 平时展示账号、状态和最近验证时间；将检查及重新登录放在次要操作中。 |

## Cookie 能解决什么

Cookie 是浏览器向网站证明当前会话的一类凭据。网站也可能把认证相关数据放在 Local Storage、IndexedDB 等位置。因此保存一段 `name=value` 字符串并不总能完整恢复登录。Playwright 提供认证状态导出和恢复，支持 Cookie、Local Storage，并可包含 IndexedDB；Session Storage 需要另外处理。[Playwright 认证文档](https://playwright.dev/python/docs/auth)

完整浏览器档案能保留更多浏览器状态；同一档案不能由多个浏览器实例同时使用，所以仍需单账号互斥管理。[持久化浏览器文档](https://playwright.dev/python/docs/api/class-browsertype#browser-type-launch-persistent-context)

Cookie 本地到期时间与平台服务器是否认可该会话是两件事。修改本地到期时间、反复加载旧快照或定时访问网页，不能保证维持平台已撤销的登录。服务器可以使用空闲超时、绝对超时或风险事件要求重登。[MDN Cookie 文档](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)、[OWASP 会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#automatic-session-expiration)

## 本机独立实验

使用当前环境的 Playwright 1.61.0、临时 Chromium 档案和只在本机运行的合成网页。没有使用社媒账号或访问社媒平台。

| 数据 | 浏览器正常关闭后重开原档案 | 加密快照恢复到新上下文 |
|---|---|---|
| 持久化 Cookie | 保留 | 恢复 |
| 会话 Cookie | 未保留 | 恢复 |
| Local Storage | 保留 | 恢复 |
| IndexedDB | 保留 | 恢复 |
| Session Storage | 未保留 | 本次快照未包含，也未测试恢复 |

同时确认 DPAPI 加密、解密可以完整还原合成快照。这说明双层保存具有技术可行性；不能据此宣称七个平台长期免扫码。结果保存在本机 `.cache/session-research/experiment.json`，实验代码和合成数据不进入发布包。

## 建议的默认流程

1. 用户点击某个平台的“登录”，软件打开该平台的专用浏览器；按平台支持的方式扫码、短信或账号登录。
2. 平台服务端确认身份后，保存浏览器档案和加密快照。界面只有在保存完成后才显示“登录已保存”，并显示昵称或脱敏账号信息。
3. 再次打开软件先展示保存的账号。采集时自动检查；平台认可后直接执行，不让用户再点一次“验证登录”。
4. 临时网络问题显示“连接异常，稍后重试”，保留最近成功认证信息及档案，不当作退出登录。
5. 需要滑块、短信或手机确认时显示“需要完成验证”，打开对应页面；只有明确登录失效才要求重新登录。
6. 长任务遇到上述情况保存进度。验证完成后接续同一任务，已保存的数据去重，沿用现有恢复策略，不宣称所有平台都有精确游标续传。

后台启动、最小化和需要人工操作时显示窗口需要单独做 Windows 体验验证。不能把“换成无界面浏览器”当作保证七平台兼容的捷径。同批任务复用浏览器有助于减少反复打开窗口；空闲后保存并释放资源。

## 保存及恢复规则

- 主档案继续使用用户数据目录，绑定平台、账号和浏览器种类。新增记录需迁移现有抖音档案，不能用空目录覆盖它。
- 快照在服务端确认登录后保存，必要时随有效凭据变化更新，采用临时文件写入后原子替换。网络错误、取消或验证失败不能覆盖最近的有效快照。
- 快照以 Cookie、Local Storage、IndexedDB 为基础；仅在平台验证证明必需时补充 Session Storage，按来源域隔离。不能笼统承诺任何浏览器内部状态都能完整导出。
- Windows 使用当前账号的 DPAPI 保护额外快照；不把它当作跨电脑通用备份。浏览器档案仍由浏览器自身管理，不能声称所有档案文件都已由本程序额外加密。[微软 DPAPI 文档](https://learn.microsoft.com/en-us/windows/win32/seccrypto/example-c-program-using-cryptprotectdata)
- Agent 只需要账号标识、认证状态及任务接口，不需要拿到 Cookie 明文。诊断、源码、演示数据和导出报告中排除认证快照。
- 用户“忘记此账号”时清理本机档案及快照；不能在下次启动时自动恢复被用户删除或退出的会话。“清理任务记录”继续不影响账号。
- 对已确认服务器撤销的快照标记不可恢复；快照用于恢复本地保存问题，不能反复尝试把失效会话恢复成已登录。
- 浏览器连接只供本机程序使用。当前启动参数包含 `--remote-debugging-address=0.0.0.0`，应改成本机地址并验收实际监听范围；本次没有据此断言外网可以连接。

## 替代方案与开源复用

| 路线 | 优点 | 对本项目的判断 |
|---|---|---|
| 专用浏览器档案＋Playwright 状态快照＋Windows DPAPI | 用户仅首次登录；软件可管理启动、保存、恢复和任务 | 推荐默认，当前项目已经具备大部分基础 |
| 手工复制 Cookie | 调试时快捷 | 不作为普通用户流程，容易遗漏状态、域和有效期信息 |
| Chrome 官方连接现有会话／Playwright 扩展 | 可以直接使用日常浏览器中已登录的会话 | 可作为后续可选入口；需要配置或授权，日常浏览器关闭、换账号及用户操作会影响任务 |
| CookieCloud 同步 | 已有 Cookie 与 Local Storage 同步实现 | 对单机软件增加扩展及服务配置，暂不作为默认依赖 |
| 在 WebView2 里重做七平台登录 | 视觉上统一到软件窗口，WebView2 自身可持久化 | 会改变现有采集器使用的浏览器环境，需要逐平台适配；优先级低于先稳定现有流程 |

日常浏览器复用并非不可行：Chrome 144+ 提供用户授权的自动连接方式，Playwright 也提供连接现有浏览器或扩展入口。它们与旧式命令行直接接管默认档案不是同一机制。不能只依据 Chrome 136 的限制就认定新版本完全不支持。[Chrome 官方自动连接](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect)、[Playwright 浏览器连接](https://playwright.dev/mcp/configuration/browser-extension)、[Chrome 136 变更](https://developer.chrome.com/blog/remote-debugging-port)

[CookieCloud 原仓库](https://github.com/easychen/CookieCloud)支持 Cookie、Local Storage 和加密同步；源码许可为 GPL-3.0。本项目已经包含 MediaCrawler 的非商业许可代码，本文不建议直接复制合并 CookieCloud 源码，也未进行许可证兼容性结论判断。

WebView2 支持在用户数据目录保存 Cookie 和网站存储，但“能保存”本身并不能证明七平台采集器可以无改动接入。[微软 WebView2 用户数据目录说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder)

## 七平台如何验收

统一保存框架，分别核对平台认证判据。下表是当前实现，不代表这些非公开网页接口有稳定性保证。

| 平台 | 当前认证判据 | 本机真实验证情况 |
|---|---|---|
| 抖音 | 当前用户 self-profile 的成功状态与有效身份；明确未登录返回单独处理 | 本次真实登录及两次恢复成功；跨天、重启电脑尚未验证 |
| 小红书 | `query_self` 返回的成功标志 | 尚无成功登录记录 |
| 快手 | 当前账号关注列表查询的返回状态 | 未完成真实账号验收，需核对判据不会误认匿名访问 |
| 哔哩哔哩 | 导航接口 `isLogin` 与未登录状态码 | 未完成真实账号验收 |
| 微博 | 移动端配置接口的 `login` 标志 | 未完成真实账号验收 |
| 贴吧 | 浏览器请求返回的 `is_login` | 未完成真实账号验收 |
| 知乎 | 当前用户接口的身份字段 | 未完成真实账号验收 |

建议先完成抖音、小红书的真实闭环，再把同一机制推广到七个平台。首轮必须覆盖：登录成功后重开软件、多个连续任务、正常关机重启、异常退出、断网恢复、程序升级、平台真实退出后重登、清理任务记录不影响账号、账号切换不串数据。

应分别统计“不需要用户操作的恢复率”“误触发重新登录次数”“需要人工操作的原因”和“保存失败次数”。跨天、跨周稳定性需要实际观察，不能用一次实验或单次扫码成功推断。

## 实施优先级

先修复未知状态误触发登录和档案路径分叉，补上登录成功后的保存确认及加密快照；随后把浏览器生命周期从单个采集任务提升到后台管理，减少重复弹窗并完成中断续接；最后再考虑日常浏览器接入、多个账号等可选能力。

默认产品体验应是“软件自动记住账号并处理恢复”，而不是让用户自己管理 Cookie。
