# 可选模板：潜客发现与采购需求分析

仅在用户的任务涉及客户、采购需求或商业线索时使用。这个模板整合了项目原有的买方强约束版、高召回版和质量复盘；不是软件的固定分析流程。用户已经说明的目标、排除项、范围、方法、字段、数量和格式优先，只有实际缺少必要信息时才问。不要要求填写目标卡、走访谈流程或再次批准模板。

## 选择适合本次需求的部分

- 找某个产品或服务的采购客户：默认使用下方的买方判断；在目标买方范围内尽量召回，再按证据强弱排序。
- 用户重视高精度：提高证据门槛，说明排除理由；不要擅自用高召回改写要求。
- 用户要更广的商业生态、供应商、渠道或合作伙伴：按其角色范围分析、分别标注角色，不把所有对象叫作买方。设备、原材料、服务本身也可以是用户的目标产品。
- 用户指定其他评分或不要评分：调整或省略 P0–P3。用户指定报告格式时直接使用；不因预置模板强制生成 Excel 和 Word。

不设置候选人数上限；用户指定数量时按其要求。少量重点展示不等于全部候选；没有命中时如实报告，不为凑数量混入无关对象。

## 可直接使用的提示词骨架

> 按用户本轮目标，从指定的数据或采集范围中找出符合条件的潜客，保留该账号本人发表的原始需求证据与可定位来源。先分清发言者、目标产品和买卖方向，再合并同平台同账号证据并排序。使用本模板中适合任务的规则；用户指定的角色范围、策略、评分和交付形式优先。信息足够便直接开始，必要信息缺失时才询问。按实际范围分批处理并保存进度，完整报告候选数量、未处理范围、账号资料缺口和判断不确定性。

这段骨架与下方规则供 Agent 执行，不要求复述给用户。用户问能力时可简短介绍：“也可以用内置的潜客分析模板，从评论中找采购需求，保留账号和原文证据；筛选方式和报告格式都可以按你的要求改。”

## 数据与证据先对齐

1. 使用 [接口流程](api.md) 查询、导入或采集。根据实际字段识别平台和 content/comment/reply/profile/event，不能见到 `payload` 就当作内容。API 输入的 `id` 是软件记录编号；`payload` 内才是原始数据，旧数据内部还可能有一层 `payload`。
2. 旧版 ZIP 按 `lead/<task_id>/<platform>/` 建索引，先在任务内精确关联 comments、raw、profiles。重复任务汇总时按稳定标识去重，保留所有来源任务；不要直接累加文件行数。
3. 评论用“平台＋评论 ID”、账号用“平台＋稳定内部账号 ID”关联。缺少稳定 ID 时只使用数据明确提供的同平台账号键，说明依据；没有可靠键则保留为未归属证据。昵称相同、头像相似或跨平台同名不能证明同一个人。
4. 区分内容作者、评论者、回复者和父评论者。需求属于实际发言账号；父评论或来源内容只提供语境，不把他人的需求转移给当前账号。
5. 程序负责解析、索引、去重和计数；买卖方向、需求与证据强弱结合原文语义判断。关键词可以帮助召回，不能代替最终判断。坏行、失败文件与未读取部分单独记录，不以预览冒充全量分析。

## 默认买方判断

此节适用于“找目标产品或服务的 B 端采购客户”。若用户要其他对象，按其目标替换角色条件。

进入买方名单前检查：证据是否直接涉及目标产品；当前账号是否表达自己的采购、询价、定制、拿样、批发、寻源或相应经营需求；是否有更强的供方广告、个人消费或无关语境推翻判断。

- “我需要定制食品包装袋，一万个，能报价吗？”是该账号的买方证据。
- “我们工厂定制食品包装袋，一万个起订，需要的联系我”是供方广告，不能因为“定制、数量、联系”就当作采购需求。
- 若用户目标是包装袋成品，采购制袋机或膜材属于相邻需求；若用户目标本来就是设备或原材料，则按该目标判断，不能套用成品排除项。
- 回复者回答父评论的价格、起订量或供货能力，不继承父评论者的采购意向。
- 企业名称、厂家身份或行业内容本身不证明采购。双重角色账号只有在其本人有目标采购证据时才作为买方候选，并说明角色不确定性。
- 高召回保留有真实弱需求、需要复核的目标候选；纯表情、无关互动、供货广告不能成为无证据的“待确认潜客”。普通消费者是否纳入由用户的目标决定。

## 可选 P0–P3 优先级

只在用户没有指定其他分级、且本次采用买方模板时使用。这是线索排序，不是成交概率或企业信用评级。

| 等级 | 判断依据 |
|---|---|
| P0 强采购 | 本人有明确采购、定制、批发、询价、拿样等动作，同时有数量、规格、用途、交期、长期需求、交易条件或明确买方身份中的至少一项。 |
| P1 明确需求 | 本人明确需要目标产品、询价、定制或拿样，但经营背景与交易细节不完整。 |
| P2 身份型买方 | 有目标相关的本人证据，采购意图较弱，且资料明确显示相关经营或买方身份；写清身份依据，不能仅凭昵称猜测。 |
| P3 待复核买方 | 有目标相关的真实弱采购信号，但采购计划不足以确认；说明具体疑点。 |

先满足本次目标角色，再分级；P2/P3 不用于凑数。小数量不自动降级，不设置武断的 B 端最低采购量。

同一账号汇总一行，保留全部关联证据。以最能证明目标需求的本人原文作为最强证据；优先级改变时，同步更新原文、证据 ID、来源链接、理由和标签，不能只升级等级。

## 账号、来源与补采

需要账号定位、潜客名单或补采时读取 [公开账号与数据质量](public-accounts.md)。公开账号、内部 ID、哈希分栏；公开号缺失就留空，不猜测、不拿内部 ID 补位。业务证据充分但公开号缺失的候选仍可保留，并记录补采需求。

证据保留原文、发言账号、平台、评论或内容 ID、父评论 ID（若有）、原链接、任务与采集时间；另用软件的 `evidence_ids` 引用输入记录。原文与分析理由分开。账号主动公开的商务联系方式可以按用户需要整理并注明来源，不把第三方号码归给当前账号；用户要求整理线索不等于授权自动联系。

## 默认交付与保存进度

用户未指定其他格式时，可交付 Excel 全量明细＋Word 重点摘要。建议字段为平台、昵称、公开账号与类型、内部 ID、主页、角色、可选 P 级、最强原文、判断依据、需求标签、证据 ID、来源链接、来源任务、采集时间、资料状态及待核实事项。字段、工作表和报告结构可以按任务修改。

- Excel 一行一个账号，按用户规则排序；可附全部证据、账号补采和数据质量。账号与长 ID 写成文本，保留前导零；链接可点击，未知值留空。状态、缺失原因和不确定性可在相应列明确说明，不用占位文本冒充账号或联系方式。
- Word 展示重要发现与适量证据卡，并说明只是摘要。重点人数按用户需要和实际内容决定，不固定 Top 20；没有值的可选字段整项省略。与明细使用同一份数据统计。
- 使用 `/analyses` 固定输入范围，在 metadata 中记录 `template: "lead-analysis"`、实际采用的角色/策略/评分/字段，便于另一会话接续；这些字段是 Agent 自定元数据，后台不会执行评分。
- 分批处理时保存 processed_ids、真实失败/跳过原因。跨批次账号先在工作文件中合并全部证据，定期作为附件保存账号索引、已判读证据与待完成范围。恢复时读取原分析、已有结果和最新检查点，不只凭当前一页重新创建同名分析。
- 当前 results 为追加式保存，账号尚未汇总完成时不要反复追加同一账号的临时行。完成该账号相关证据归并后提交最终行，可用“平台＋稳定账号键”生成固定的 result.id；查询已保存结果避免重复，网络重试复用同一请求编号和 batch_id。同一个结果 ID 不能覆盖为不同内容，需要更改已交付规则时创建关联原分析的新分析版本。
- 简单表格可直接调用 export；多工作表、排版 Word 等定制文件由 Agent 生成后通过 attachments 保存回软件。完成前检查覆盖率，处理完的无命中记录也记入 processed_ids；未完成时保留真实状态和可恢复的检查点。

## 交付核对

核对用户目标、角色范围、同账号证据归属、去重、最强原文与评级一致性、公开账号来源和链接。采用 P 级时，P0–P3 合计应等于该分级范围内的账号数；其他角色不冒充买方计入。摘要数量、明细行数和保存成果一致。

按平台分别报告处理覆盖率、主页覆盖率、公开号覆盖率和失败范围。没有人工标签时，潜客准确率写“未验证”；结构检查通过不等于语义正确，不复用历史样本的成功率作为本轮结果。
